# План: проверка README на битые ссылки и отсутствующие файлы (v4)

Правка v4 по решению оркестратора (Алисы), разрешённый 4-й круг:
1) приоритет правил «runtime-артефакт» над «токен с расширением»;
2) сверка автопрогона и ручного списка только по вхождениям класса
   «ссылка», фрагмент — весь спан целиком, несколько совпадений в
   одной строке считаются по числу вхождений;
3) класс «спец-метка» для `[БЛОК]` и подобных спанов.

## Уточнения после круга 4 (решено по решению оркестратора)

- Порядок применяемых правил (итог): 1 → 3 → 4 → 2 → 8 → 5 → 6 → 7.
  Правило 4 (команда) стоит ВЫШЕ правила 2: спан, начинающийся с
  `pip`/`setx`/`python`, никогда не проверяется на существование
  целиком, даже если он заканчивается на расширение
  (`pip install -r requirements.txt`, `python orchestrator.py <режим>`
  не станут «файлом»); по правилу 2 проверяется только путь-аргумент
  внутри команды.
- Проход A: шаблоном ловится ПОДСТРОКА-якорь, затем выделяется
  минимальная объемлющая конструкция ссылки целиком (от открывающего
  `[` до закрывающего `)`, либо `<...>`, либо `href="..."`, либо
  bare URL до пробела). Фрагмент A — вся эта конструкция. Если в
  одной конструкции сработали два разных шаблона (`](` и `https://`)
  — это ОДНО вхождение класса «ссылка», подстроки не удваиваются.
  URL внутри бэктик-спана ссылкой не считается: это кодовый спан,
  правила про бэктик-спаны старше класса «ссылка» — такие совпадения
  из прохода A исключаются. Fenced-блоки: если найдутся, их строки
  обрабатываются построчно как отдельные фрагменты.
- Цель ссылки из правила 1, совпавшая с runtime-файлом или локальным
  секретом (правило 3), получает вердикт правила 3, а не «битая»:
  правило 3 в перепроверке цели ссылок имеет старшинство над
  проверкой существования.
- Прямое покрытие правила 8 — спан `[БЛОК]` на строке 27 README
  (в тексте v4 ранее стоял ошибочный пример `[[БЛОК] ]]`; в README
  двойных скобок нет — исправлено по факту).
- Проход B выписывает вдобавок к бэктик-спанам plain-упоминания
  файлов в круглых скобках вне спанов (например,
  `(project_report.txt)` на строке 15 README) — они классифицируются
  по тем же правилам.
- Метка «✅ Обработать №N» в README — обычный текст в кавычках, не
  бэктик-спан; правило 8 как класс применяется к ней, если она
  встречается в перечислении строк прохода B, но в список спанов не
  входит.
- В «битых ссылок: N» входят только битые цели ссылок по правилу 1
  и отсутствующие файлы по правилу 2, не снятые правилом 3.
- Нумерация «1 → 3 → 4 → 2 → 8 → 5 → 6 → 7» здесь — только смысловая
  ссылка на правила; от рендера markdown-списка порядок применения
  не зависит.

## Цель

Проверить, что `README.md` не вводит в заблуждение: в нём нет битых
markdown/HTTP-ссылок, а файлы, на которые он прямо указывает, либо
существуют, либо штатно создаются/читаются кодом при работе. Итог —
отчёт в чат; файлы проекта не изменяются. `README.md` только читается.

## Метод и единица счёта

Единица счёта — «вхождение» (строка README + позиция шаблона в ней).
Если в одной строке шаблон совпал несколько раз, это несколько
отдельных вхождений (по числу совпадений, не одна строка — один счёт).
Отдельно ведётся множество уникальных путей для таблицы существования.

«Фрагмент» — ВСЕЙ бэктик-спан или вся конструкция ссылки целиком,
 как она есть в README, без сопоставления по подстроке.
Совпадение по подстроке запрещено: совпадение есть, только если
фрагменты равны посимвольно и лежат на одной и той же строке.

Сверка автопрогона (A) и ручного списка (B) ведётся ТОЛЬКО по
вхождениям класса «ссылка» (правило 1). Спаны (бэктик-метки,
команды, идентификаторы и т. д.) в сверку A и B не входят: их
покрытие проверяется отдельным проходом — полным списком спанов B
против полной классификации, каждый спан обязан получить класс и
вердикт. Расхождение любого пункта = артефакт, который объясняется
в отчёте, а не подгоняется.

- Проход A (авто): PowerShell `Select-String` с `-AllMatches`
  (rg в этой среде не установлен) по шаблону ссылок
  `\]\(|<https?://|href=|https?://` поверх README. По вхождению
  фиксируется номер строки и фрагмент.
- Проход B (ручно-машинный): построчный разбор README (все строки
  выводятся). Из строк выписываются: все вхождения класса «ссылка»
  (по правилу 1) — они идут в сверку с проходом A; все бэктик-спаны
  целиком — они идут в отдельную сверку классификации.

## Классификация вхождений и порядок применения правил

Правила применяются ПО ПРИОРИТЕТУ, не «1 → 7 по номерам». Явный
порядок: 1 (ссылка) → 3 (runtime-артефакт / локальный секрет) →
2 (файл/путь) → 8 (спец-метка) → 4 (команда) → 5 (плейсхолдер) →
6 (идентификатор) → 7 (без класса). Правило 3 старше правила 2:
если спан уже признан runtime-файлом или локальным секретом,
проверка существования по правилу 2 к нему не применяется, действует
вердикт правила 3.

1. Markdown/HTML-ссылка: `[текст](url)`, `![](...)`, `<url>`,
   `href="..."`, bare `https://...`. Для найденной цели: якоря и
   query отрезаются (`...#sec`, `...?x=1`); локальная цель —
   существование файла ИЛИ каталога от корня репо; внешняя —
   `Invoke-WebRequest -Method Head`: код 400+ = битая; сбой сети,
   таймаут = «не проверено»; редирект 200/3xx = «ок».
3. Runtime-файлы и локальный секрет: отсутствие в репо ШТАТНО,
   приоритет над правилом 2. Верифицируется по коду проекта:
   `warm_leads.db`, `data/warm_leads_log.txt` — создаёт
   `warm_leads.py` (`DB_PATH` строка 15, `LOG_PATH` строка 16);
   `project_report.txt` — создаёт `orchestrator.py` (`REPORT_FILE`
   строка 18); `токены.txt` — кодом не создаётся, это локальный
   секрет, который читают `start*.bat` и который не лежит в репо
   (`.gitignore`); его отсутствие на машине нормально и не битое.
   Если такой файл есть на диске — вердикт «ок, локальный».
2. Файл/путь (после правила 3): бэктик-токен с расширением файла
   (`.py`, `.txt`, `.bat`, `.db`, `.log`, `.yaml`, `.md`) или
   конфиг с ведущей точкой (`.gitignore`), не попавший под правило
   3. Проверка существования от корня репо, подсчёт в уникальных
   путях.
8. Спец-метка: бэктик-спан вида `[БЛОК]`, `[токен]`, метки и флаги
   в квадратных скобках, а также скобочные пометки вроде
   `«✅ Обработать №N»`. Это не файл и не ссылка: вердикт «метка,
   не проверяется». Прямое покрытие — спан `[БЛОК]` из строки 27
   README и любые подобные.
4. Команда: спан начинается с `pip`, `setx`, `python` — спан целиком
   не проверяется, но путь-аргумент внутри (`requirements.txt` в
   `pip install -r requirements.txt`) классифицируется по правилам
   3→2 в указанном порядке.
5. Плейсхолдер: `<режим>` и подобные угловые заглушки — не ссылка,
   не проверяется.
6. Идентификатор: токен с ведущим `/` без расширения (API-эндпоинт
   `/web/1/js/items`, команда бота `/лиды`), ключ-значение
   `KEY=value` (`sort=DATE_DESC`, `BOT_ROLE=owners`), одиночное
   слово без расширения (`setup`, `test`, `parse`, `report`, `all`,
   `is_by_homeowner`) и env-переменные (`BOT_TOKEN`,
   `BOT_TOKEN_OWNERS`, `WARM_LEADS_DB`, `WARM_LEADS_LOG`,
   `REALTOR_CHAT_ID`, `BOT_ROLE`). Вердикт один: «не файл, не
   проверяется на существование».
7. Списки классов не закрытые: любой новый спан классифицируется
   по этим правилам; если ни одно правило не подошло, спан получает
   класс «без класса», фиксируется в отчёте отдельной строкой —
   это тоже вердикт, «ни один спан без вердикта» выполняется
   буквально.

## Ожидание и отчёт

Ожидание (наблюдение до факта, не предзаданный результат): в README
нет markdown/HTTP-ссылок вовсе. Если ссылка найдена — применяется
правило 1, сам факт ссылок не дефект; дефект — битая цель.
Отчёт в чат содержит: полное число вхождений обоих проходов отдельно
по классу «ссылка» (для сверки A и B), полный список бэктик-спанов
с классами и вердиктами, таблицу уникальных путей (путь — класс —
есть/нет — почему), число файлов с расширением (существует /
runtime / битое) и вывод «битых ссылок: N».

## Что НЕ меняется (границы правки)

- Содержимое `README.md` не редактируется.
- Скрипты, боты, базы и конфиги проекта не трогаются.
- Из файлов меняется только этот план в `plany/`; результат — отчёт
  в чат, без отдельных файлов.
